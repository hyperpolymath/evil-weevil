= Architecture Decision Record: 0011-publishing-and-credentials

== 11. Where the repository is published, and what a credential may touch

Date: 2026-09-20

=== Status

Accepted (records what was measured while publishing; two items left deliberately open).

=== Context

The repository was minted, built and gated entirely locally. Publishing it needed a
remote, and a remote needs a credential. Three were presented during the session and
each failed or succeeded for a different, measurable reason — which is the material
this ADR exists to keep, because every one of those reasons will recur on the next
repository in this estate.

=== Decision

==== 1. The repository is published at `hyperpolymath/evil-weevil`, as staging

The brief calls for `metadatastician/evil-weevil`. Creating or transferring a
repository into an organisation requires `Administration: write` on that organisation,
and the credentials presented held it for neither route:

* `POST /orgs/metadatastician/repos` -> "You need admin access to the organization
  before adding a repository to it."
* `POST /repos/hyperpolymath/evil-weevil/transfer` -> "Resource not accessible by
  personal access token".
* And the organisation refuses classic tokens outright, org-wide policy:
  "`metadatastician` forbids access via a personal access token (classic). Please use a
  GitHub App, OAuth App, or a personal access token with fine-grained permissions."

So the repository currently lives at `github.com/hyperpolymath/evil-weevil`, private,
with the complete history (10 commits, `main` = `9e1ef76` at the time of writing) and
all 35 workflow files intact. The intended canonical home remains
`metadatastician/evil-weevil`; a transfer needs an org admin to create it or an org
admin's `Administration: write` on a token — a browser click, not a code change.

==== 2. The identity strings in the tree are NOT rewritten to the staging location

55 occurrences of `github.com/metadatastician/evil-weevil` across 30 files — including
`CITATION.cff`, the deed, `www/.well-known/security.txt`, `www/.well-known/aibdp.json`,
`build/container/Containerfile`, `build/guix.scm` and the CODEOWNERS file — name the
repository's home. They are not broken links to be swept: they are identity, and
identity that a transfer would have to un-rewrite byte for byte.

Rewriting them now would make the tree describe a staging location as if it were
permanent, and would have to be reverted the moment the repository lands where the brief
says it belongs. Keeping them is the smaller lie: the links 404 until the transfer, and
this ADR is the note that says so. When the transfer happens, one grep and one replace
is the entire edit.

==== 3. What a credential may touch

* **Never in the tree.** No token in any file, in `git config`, or in a committed
  artefact. The remote URL is stored without credentials and authentication is supplied
  per operation.
* **Never after use.** A token pasted into a chat is treated as public from that moment,
  recorded nowhere, and revoked after the operation it was issued for. Three were
  presented during this session, including a classic one carrying `admin:org`, `repo`,
  `workflow` and `user` across the whole account; that one is the reason the rule exists.
* **Least privilege, measured not assumed.** A fine-grained token was verified to hold
  `Contents: write` on exactly one repository by pushing a probe branch and deleting it.
  Prefer single-repository scope and a short expiry (the one used expires in seven days).
* **Deploy keys are the credential-free route.** For a repository that already exists,
  an SSH deploy key with write access gives one-repository write without a PAT at all —
  and it sidesteps the classic-token ban entirely, since that ban is about tokens.

==== 4. Private repositories do not get free runners, and this one has no runners at all

Pushing to a private repository started 27 workflow runs. 23 failed with zero steps
executed: "The job was not started because recent account payments have failed or your
spending limit needs to be increased." Every job reported `steps: 0`, so nothing in this
repository was ever exercised by CI.

This matters beyond the inconvenience. The project's claim is that the seam is
mechanically gated; the gates run perfectly in a clean local tree (ADR-0006, `just
seam-check`, 5/5 self-test), but a reader looking at a red badge would conclude the code
is broken, and the conclusion would be wrong in a way that flatters nobody. Options, in
the order this ADR recommends them:

* **Public, so the gates run on free standard runners** — consistent with the estate's
  house style, where proof status is published rather than asserted. Existing public
  repositories in the same organisation are the precedent.
* **Fix the account's payment state and set a spending limit**, if private is required.
* Either way: **do not read a red badge as a code failure** until one of the two is done.

=== Consequences

* The repository is real, complete and on a remote that whatever is to hand can reach.
  The publish path is proven end to end: 36 workflows registered, `main` in sync with the
  working tree, the pre-publish scan for secret-shaped strings in history clean.
* Transferred, the ADR needs one amendment and one grep; nothing else in this decision
  is location-dependent.
* Two items stay OPEN on purpose: the canonical home (needs org admin), and visibility
  (a publishing decision, not an engineering one). Both are recorded in `STATE.a2ml`
  rather than silently defaulted.
* The mirror workflow (`mirror-reusable.yml`) is inert here — zero repository secrets are
  configured, so it has no credential to publish anywhere with, whatever it is pointed at.
  That is a property of this repository's state, not a property of the workflow.
